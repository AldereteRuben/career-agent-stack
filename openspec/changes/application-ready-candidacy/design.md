# Design

## Context

Existing foundations (observed at PR #129 head `8a7f571`): `document_versions` stores approved PDFs with `claims`, `claimsBasis`, `language`, `paperSize`; `applications.document_id` already points at `document_versions` through the composite foreign key `applications_workspace_document_fk` (no `ON DELETE` action, so deleting a linked document is refused); `DELETION_ORDER` in `apps/api/src/workspace-deletion.ts` deletes `applications` before `document_versions`; the JSON export in `apps/api/src/server.ts` refuses artifacts over 30,000,000 bytes with `413 EXPORT_ARTIFACT_LIMIT`. `packages/domain/src/ai-documents.ts` defines derived claims with source fact ids and currentness; `apps/api/src/ai-document-routes.ts`, `document-renderer.ts` and `document-reuse.ts` render and reuse resumes; the assistant has a consented preview/run flow (ADR 015, `docs/operations/assistant.md`); backup and deletion follow ADR 019 and 020. Cover letters, plain-text output and ZIP do not exist. `openspec/specs/` is empty, so all capabilities are new.

There is no route that deletes one application; deletion is workspace deletion through the deletion job.

Everything here is blocked on PR #129 CI green and merged; details may shift when rebasing on `main`, so each task begins by re-reading the files it touches.

## Goals / Non-Goals

**Goals:** offer-specific resume and cover letter from approved facts; human review and approval; PDF plus text; one language per version; optional per-draft-confirmed Codex rewording; application ZIP; export, backup, restore and workspace-deletion coverage (including files); later follow-up draft.

**Non-Goals:** submission automation (#43), sending email, mailbox access, AI for follow-up, DOCX, mixed languages, multi-application ZIPs, persisting package selections, deleting an individual application or revision (no such route exists), per-workspace file deletion (the existing job empties the whole files folder for this one-workspace installation; isolating files per workspace would need durable per-file paths in `deletion_jobs`, an ADR 020 update and a migration, which is a separate change), converting the existing `applications.document_id` resume, version or changelog changes.

## Decisions

1. **Three kinds of sentence (B1).** Every sentence is one of:
   - `OFFER_REFERENCE`: produced only by a fixed per-language template that inserts offer fields (company, role, location) verbatim, e.g. "I am applying for {role} at {company}". It makes no statement about the candidate and cites no fact. Only the local builder can create it; an edited sentence, a Codex proposal or a user-written sentence can never be `OFFER_REFERENCE`.
   - `BOILERPLATE`: a fixed per-language salutation or closing from the builder's phrase table (for example "Atentamente", "Sincerely"). It says nothing about the candidate or the offer and cites no fact. Rewording it (for example "Best regards") keeps it `BOILERPLATE` as long as the no-new-fact check finds no employer, title, date, number, credential or skill in it; otherwise it becomes a `CANDIDATE_CLAIM`. This keeps the "written by you, not backed by a profile fact" warning meaningful, since it is not raised for plain greetings. A Codex proposal can never be `BOILERPLATE`.
   - `CANDIDATE_CLAIM`: any statement about the candidate's experience, skills, education, dates or numbers. It SHALL cite at least one approved fact of the same workspace, and every employer, title, date, number, credential and skill it contains must appear in a cited fact. Offer text never counts as support: an offer's company or role in a candidate claim is checked against the cited facts, not the offer.
   A sentence cannot become an `OFFER_REFERENCE` by editing: an edited `OFFER_REFERENCE` that adds anything beyond its template becomes a `CANDIDATE_CLAIM` and must pass the citation rules (or be confirmed as "written by you, not backed by a profile fact", `origin = USER_UNSUPPORTED`; see decision 3). The reused `ai-documents.ts` claim contract is extended with `kind` and `origin`; contract version is bumped only if `main` requires it.
2. **Local builder first, Codex as optional rewording (S7).** The deterministic builder in `packages/domain` produces the baseline and is the only way content enters a draft. Codex never drafts from scratch: it receives the builder's existing sentences with their cited facts and proposes rewordings only. This scope is the same in the proposal, the specs and the tasks. Rewordings are validated by citation and "no new fact" checks (entities, numbers, dates and skills must appear in the cited facts); rejection leaves the draft untouched.
3. **Fact, citation and edit validation is a server rule, not a client hint (S1).** On every edit save, on approval and on each assistant proposal, the server checks that every `sourceFactIds` entry exists, belongs to the request's workspace, and is `APPROVED` at that moment. Any violation rejects the write with a code naming the sentence. Citations are validated again when staleness is computed on read. For an edited `CANDIDATE_CLAIM` the server also runs the *no-new-fact* check against the cited facts: every employer, title, date, number, credential and skill in the sentence must appear in a cited fact (the same check used for Codex output). Each sentence of a save ends in exactly one of three states:
   - **Supported edit:** valid citations and no new fact. It keeps its citations and is saved. Origin rule: an edit that changes the text of a `BUILDER` or `CODEX` sentence makes its origin `USER_EDITED`, so the review shows what Codex wrote and what the person changed; an unchanged sentence keeps its origin.
   - **Rejected edit:** invalid citations, or a new fact with no explicit confirmation. The save fails with `422 UNSUPPORTED_CONTENT` (or the citation code) naming the sentence and the offending skill, number or date; nothing is stored.
   - **Confirmed unsupported claim:** the person resubmits the sentence with `confirmUnsupported: true`. It is stored with `origin = USER_UNSUPPORTED`, keeps whatever valid citations it has (possibly none), and is shown as "written by you, not backed by a profile fact". Confirmation at save is not approval: the approve request must list the id of every `USER_UNSUPPORTED` sentence it was shown, and any missing or extra id gives `409 UNSUPPORTED_NOT_CONFIRMED`. The confirmed ids are recorded on the revision (`confirmed_unsupported_ids`). `USER_UNSUPPORTED` sentences are never sent to Codex, and an edit that makes them supported (valid citations, no new fact) returns them to `USER_EDITED`.
4. **Immutable preview artifact; approval binds to its stored bytes (S2).** Chromium PDF output can embed time-varying metadata (creation date, document ids), so the same claims can produce different bytes on each render. Approval therefore never re-renders and re-hashes.
   - **When rendered and stored:** the text and PDF of a revision are rendered exactly once, when the revision is saved (draft creation, an edit, accepting Codex proposals, or a paper-size change each create a new revision), from that revision's stored claims. Both files are written with their SHA-256 (`text_*`, `pdf_*` are not null from creation). If rendering fails, the save fails and no revision is created. The review screen shows and serves these stored bytes as the preview; no other render exists.
   - **What the editor receives:** `revisionId`, `contentHash` (SHA-256 of the canonical claims JSON), `textSha256`, `pdfSha256` (digests of the stored preview), `factsHash` and `offerHash` (computed when the revision was saved), and the `USER_UNSUPPORTED` sentence ids.
   - **At approval the server:** (1) loads the revision and requires it to be pending and the newest; (2) reads the stored text and PDF and checks that their SHA-256 equals the stored digests and the digests sent (detects corruption or tampering, no rendering); (3) recomputes `contentHash` from the claims and `factsHash` and `offerHash` from the database and compares them with the values sent and recorded; (4) re-runs citation checks (decision 3), the language check and the `USER_UNSUPPORTED` confirmation check. Any difference gives `409 APPROVAL_STALE` (or `UNSUPPORTED_NOT_CONFIRMED`) and nothing is approved. If only a fact or the offer changed, the revision shows `NEEDS_REVIEW` and the person re-saves it, which renders a new revision with fresh hashes and a new preview.
   - **On success:** only `approved_at`, `approved_by` and `confirmed_unsupported_ids` are set, once. Claims and files are never modified, so downloads and the ZIP serve exactly the bytes the person reviewed. Revisions are immutable once saved except for that single approval write.
5. **Freshness definitions (S2, S5).**
   - `factsHash`: SHA-256 over the sorted list of `(factId, status, canonicalText)` of every cited fact.
   - **Where the offer fields come from (F1).** `company`, `role` and `location` come from the **immutable application columns** (`applications.company`, `role`, `location`, copied at creation and not editable: `applicationUpdateSchema` cannot change them). They are used by the `OFFER_REFERENCE` templates and by `offerHash`, so the template text and the staleness hash always read the same row. `job_snapshots` has no company, location or requirements column, so nothing else supplies them.
   - `offerHash` (the offer staleness hash): SHA-256 over the canonical JSON `{company, role, location}` of the application row plus `{title, description}` of the **latest `job_snapshots` row** of the application's job, with `description` = `description_text` normalized (trimmed, whitespace collapsed, line endings unified; a null `description_text` normalizes to the empty string). "Latest" means ordered by `fetched_at DESC, id DESC`, so equal fetch times still pick one row deterministically. **Derived requirements are excluded**: they are computed from the description by a skill dictionary (`extractKnownSkills`), so the description already covers any real change, and a dictionary change in a release must not turn approved documents into `NEEDS_REVIEW`. Volatile fields (fetch time, availability, source ids, `snapshot_hash`) are excluded, so only material changes alter it.
   - **Application with no offer (F1).** `offer_snapshot_id` is `NOT NULL`. An application whose `job_id` is null, or whose job has no snapshot, cannot have documents: creating a draft pair is refused with the named `409 APPLICATION_HAS_NO_OFFER`, nothing is written, and the interface explains in Spanish and English that documents need a saved offer and links to saving one. No hash rule for a missing snapshot exists because no revision can exist without one.
   - Staleness is computed on read, never stored: a revision is `NEEDS_REVIEW` when the recomputed `factsHash` or `offerHash` differs from the values recorded **when the revision was saved** (decision 4; for an approved revision these equal the values the person approved, because approval refuses a difference) or when any cited fact is no longer `APPROVED`.
6. **No superseded selection (S3).** A logical document (application, kind, language) has an ordered list of revisions. An approved revision is *superseded* once a later revision of the same logical document is approved. Only the newest approved revision, not stale, can be selected for a package or downloaded as "ready". A later *pending* edit does not supersede it but is shown beside it, and the interface warns, wherever the earlier approved revision can be selected or downloaded, that a newer unapproved edit exists. The ZIP route re-checks this at request time.
7. **Data model: one-way references, one source of truth (B2).**
   - `application_documents(id, workspace_id, application_id, kind RESUME|COVER_LETTER, language es|en, created_at)`; unique `(workspace_id, application_id, kind, language)`; composite FK `(workspace_id, application_id)` to `applications(workspace_id, id)` **ON DELETE RESTRICT**.
   - `application_document_revisions(id, workspace_id, document_id, revision, parent_revision, claims jsonb, content_hash, offer_snapshot_id, offer_hash, facts_hash, paper_size, text_storage_path, text_sha256, pdf_storage_path, pdf_sha256, confirmed_unsupported_ids jsonb, approved_at, approved_by, created_at)`; unique `(workspace_id, document_id, revision)`; composite FKs to `application_documents` and to `job_snapshots`, both **ON DELETE RESTRICT** (revisions are deleted before documents, and documents before applications and snapshots, by `DELETION_ORDER`). `offer_snapshot_id` is `NOT NULL`: an application with no job or no snapshot is refused with `409 APPLICATION_HAS_NO_OFFER` before any row is written (decision 5), and `offer_hash` is computed from the application columns plus that snapshot as defined in decision 5. `parent_revision` is the parent's revision number within the same document, a plain integer with **no self foreign key**: revisions are never deleted individually, and a composite self FK with `SET NULL` would try to null the non-null `workspace_id`. Text and PDF paths and digests are not null from creation; paths are relative to `FILES_LOCAL_PATH` and every write resolves the path and refuses one that falls outside that folder (the same containment check used when serving files, as in `server.ts`). Approved means `approved_at is not null`, and a check requires `approved_by` when approved.
   - The **new tables hold the only truth for offer-specific documents**. Nothing in the new tables is referenced by `applications`, and `applications` gains no column: there is no circular foreign key. Existing `applications.document_id` is unchanged: it keeps pointing at `document_versions` (the general resume attached today).
   - **Upgrade behavior:** the migration creates the new tables empty and does not alter, backfill or relink any existing row. An application with a linked `document_versions` resume keeps it exactly (same id, approval state, file) and the application page keeps showing it as "attached resume". It is not converted into a revision and is not selectable for the ZIP, which the interface says honestly. Rationale: a backfill would invent approvals, hashes and a text file for content that was never reviewed in this model.
   - **Deletion scope and order:** this iteration supports workspace deletion only; there is no application DELETE route and none is added. `DELETION_ORDER` gets `application_document_revisions`, then `application_documents`, both **before** `applications`, which already precedes `document_versions` and `job_snapshots`. The foreign keys are RESTRICT on purpose: rows are removed only by the ordered deletion, never by database cascade. **Files:** the existing job does not delete files by path and persists no path list; `deleteWorkspaceFiles` empties the whole `FILES_LOCAL_PATH` (and `backups/`, `logs/`, `tmp/`) after the rows are deleted in one transaction, and the `deletion_jobs` row (id and status) makes an interrupted deletion retry on the next start. Because new text and PDF files live under `FILES_LOCAL_PATH` (path-contained, see above), that job removes them with no change to its mechanism. This is correct for the one-workspace installation of ADR 020; it is not per-workspace file isolation, and this change does not add one. A coverage test fails if the new tables are missing from `DELETION_ORDER`. Deleting a `document_versions` row that an application still links stays refused by the existing foreign key; workspace deletion removes applications first, so the order is valid.
8. **Text output from the same claims as the PDF** by one function, stored with a SHA-256 like the PDF. PDF rendering reuses `document-renderer.ts` for the resume layout and adds a cover-letter layout (A4 and Letter) in the same module; both files are rendered once when the revision is saved (decision 4), never at approval or download.
9. **Package selection is request-only (B4).** The ZIP route takes a list of revision ids in the request body and persists nothing: no selection table, no column, no export or backup rows for selections. Every proposal-level guarantee about selections (export, restore, deletion of selections) is therefore removed from the specs and tasks.
10. **ZIP built on demand and streamed (S4, S9).**
   - Limit: at most **20 documents** (selected revisions). Each contributes a PDF and a text file, so at most 40 content files plus one `manifest.json`, 41 entries. Also at most 30,000,000 uncompressed bytes in total (the same constant as the export limit); over it returns `413` and nothing is produced; no document is silently left out.
   - Names are safe (no path separators, no control characters), unique, and may contain accents. Entries whose names are not ASCII set the ZIP general-purpose flag bit 11 (UTF-8); a test reads the local and central headers.
   - The manifest lists file name, kind, language, revision, approval time and SHA-256 per file, plus a plain notice that the ZIP is not encrypted and is attached manually. It carries no profile data, notes or contact details; the only personal content is what the approved resume and cover letter print.
   - Needs a small zip writer dependency or a hand-written store-only writer; choose after checking the dependency policy and licenses (`THIRD_PARTY_NOTICES.md`).
11. **JSON export (S4).** The export gains `applicationDocuments` and `applicationDocumentRevisions` rows with claims, origins, hashes and approval data, and the revision texts inline for every revision. PDF bytes are bounded so that revision history cannot make the whole export fail:
   - PDF bytes are added as export artifacts only for **approved revisions** and for the **newest pending revision** of each logical document. *Newest pending* means the revision with the highest revision number of a logical document, when it has no `approved_at`; if the highest revision is approved, the document has no newest pending revision.
   - Every other (historical, unapproved) revision is exported with its text inline and its `pdf_sha256`, and its row is marked `pdfIncluded: false`; the digest lets the person verify a PDF they kept. These PDFs are not lost from the workspace, they are only not duplicated into the export.
   - Included PDFs count in the existing `totalArtifactBytes` check. If the total still exceeds 30,000,000 the existing `413 EXPORT_ARTIFACT_LIMIT` is returned; no row, text or included PDF is dropped silently to fit. Approved revisions still accumulate by explicit approvals only; this is stated as a limit.
12. **Assistant consent for documents (B3), synchronous and in memory (N2).**
   - Document AI always requires a confirmation for *that draft*. A remembered or standing consent (`ai_consents`) and any automation policy never authorize a document request; the route ignores them for this action type.
   - **Provider input (G4).** `executeCodex` accepts only an `AiSourceSnapshot` and builds its prompt with `buildAiPrompt` (common instructions, operation instructions and the canonical JSON of the snapshot's source data). `DOCUMENT_REWORD` therefore adds, in `packages/domain/src/ai.ts` and `apps/api/src/ai/prompts.ts`:
     - **a `DOCUMENT_REWORD` variant of `AiSourceSnapshot`** holding the offer fields chosen (company, role, location) and, per candidate-claim sentence, `{sentenceId, text, kind, citedFacts: [{factId, text}]}` (only `CANDIDATE_CLAIM` sentences; `kind` is always `CANDIDATE_CLAIM` in a valid snapshot), in a fixed order;
     - **an output schema** in `aiOutputSchemas`: a list of `{sentenceId, text, sourceFactIds}`, with no other field;
     - **operation instructions** in `operationInstructions`: reword only the given sentences, keep every cited meaning, cite only the given fact ids, add no employer, title, date, number, credential or skill;
     - **data categories** in `aiOperationDataCategories`: exactly the existing categories `APPROVED_FACTS` and `JOB_POSTING` (`packages/domain/src/ai.ts`), with no new category. The one-off consent's `data_categories` lists exactly those two.
   - **Payload bytes and hash.** The server builds the snapshot **deterministically** (same sentences, facts and offer fields give the same bytes), then the messages with `buildAiPrompt`. `payloadSha256` is the SHA-256 over the exact `buildAiPrompt` messages that are sent to Codex (canonical serialization of the message list). The preview displays those messages in full (instructions, offer fields chosen and **every sentence** with kind, cited fact ids and cited fact texts) and returns `payloadSha256`. The confirm request carries that hash; the server rebuilds the snapshot and messages with the same functions, compares, and sends only if equal (else `409 PAYLOAD_CHANGED`). The messages passed to the provider are the messages hashed, so preview, hash and dispatch bytes are the same thing.
   - **Smaller design chosen: rewording is a synchronous, in-memory request**, not the existing asynchronous queue. The existing manual run path enqueues the whole source snapshot into `ai_runs.snapshot` (not null) and stores outputs as `ai_artifacts` rows awaiting review, which would persist the sentences and the proposal text this design forbids; the document rewording therefore does not call `queue.enqueue`, create `ai_artifacts` rows or store a snapshot of text. The confirm request calls the provider, validates the output (decision 3 and 2.4) and returns the validated proposals **in the response only**. The server keeps them in memory for the duration of the request and persists only hashes and identifiers.
   - **Run contract (F2).** The synchronous run still obeys the controls the queue enforces, because `executeCodex` leaves consent, leases and usage recording to its caller:
     - **Operation (G1):** `DOCUMENT_REWORD` is added to `aiOperations` in `packages/domain/src/ai.ts` (name within the column limit). The database also checks the operation: `ai_runs_operation_check` (migration 0010) lists only the four existing operations, so task 1.2's migration drops and re-adds that constraint with `DOCUMENT_REWORD` added and still rejecting any unknown operation; the Drizzle schema and snapshot are updated with it. No other task adds a migration for this.
     - **Consent:** each explicit confirmation inserts one `ai_consents` row for `DOCUMENT_REWORD` with `remembered = false` (this gives `ai_runs.consent_id` its non-null foreign key), with `data_categories` as above and the next `revision` under `ai_consents_revision_uq`. Remembered rows are never read for this operation; single use is already enforced for non-remembered consents.
     - **Run row:** the `ai_runs` row is inserted **directly with `status = 'RUNNING'`, never `QUEUED`**, with every `NOT NULL` column defined (`consent_id`, `connection_id`, `idempotency_key`, `content_identity`, `account_lock_key`, `snapshot_hash`, `input_versions`, `reserved_day`) from the same helpers the queue uses, `operation = DOCUMENT_REWORD`, and an insert-time `snapshot` value holding only the hash-only record below (no proposal hash, which does not exist yet). It ends `SUCCEEDED`, `FAILED` or `CANCELLED` (by the route; see the next two bullets), or `INTERRUPTED` by recovery. The worker claims only `QUEUED` rows, and `queue.enqueue` is not called.
     - **Generic queue passes skip it (G2).** The worker's claim loop, every enqueue and `recoverAfterRestart` run `cancelInvalid`, which scans `QUEUED` **and `RUNNING`** rows and calls `authorization()`; that returns null when `run.snapshot` does not parse as `AiSourceSnapshot`, and `requestCancellation` would then move a `RUNNING` row to `CANCEL_REQUESTED`. A hash-only snapshot never parses. `cancelInvalid` therefore **skips `DOCUMENT_REWORD` rows in its validity pass**: the generic authorization is not applied to them and the validity pass never moves them to `CANCEL_REQUESTED`. Their validity is checked by the route itself (consent, payload hash, base revision) before the row is inserted. This skip covers the *validity* pass only: an explicit user cancel (`POST /api/v1/ai/runs/:id/cancel`, which accepts any run id), `revokeConsent` and `revokeConnection` still move a `RUNNING` document run to `CANCEL_REQUESTED`. The route watches for that state, aborts the provider call and itself ends the row `CANCELLED` (conditional on its lease token) and releases the lease, so the row never stays `CANCEL_REQUESTED` until the lease expires; no proposal hash is recorded. The worker still claims `QUEUED` rows only. The earlier wording "the worker never sees it" is replaced by this: the worker's passes see the row but must not claim, execute, authorize or cancel it.
     - **Lease and crash recovery (G2).** The `RUNNING` row sets `lease_token`, `lease_owner` and `lease_until`, and the route heartbeats **both the `ai_runs` row and the `ai_account_leases` row** at the queue's heartbeat interval until the run ends, using a **`DOCUMENT_REWORD`-specific route heartbeat** keyed by the run's `lease_token` (it updates `lease_until` on both rows only while the run row is still `RUNNING` or `CANCEL_REQUESTED` with that token). It does not call `queue.heartbeat` and `authorization()` is not made to return a pass for this operation; `authorization()` is simply never consulted for document runs, so a null result cannot cancel them. When the token no longer matches (recovered or cancelled), the heartbeat stops and the route treats the run as lost. The heartbeat keeps both leases valid through the maximum execution of 125 s (`AI_LIMITS.timeoutMs` 120 s plus 5 s kill grace) plus a margin, which is longer than the base lease duration (at most 120 s). If the API crashes mid-request, heartbeats stop, `expireLeases` ends the row `INTERRUPTED` once `lease_until` passes and deletes the expired account lease, so the workspace and the Codex account are unblocked and no run stays `RUNNING` forever.
     - **Exclusivity and locking (G2):** the transaction first runs `expireLeases`, then does the busy check (the account lease and any `RUNNING` **or `CANCEL_REQUESTED`** run in the workspace, the same set the queue's claim counts), the `RUNNING` run insert and the account lease write, **all in one transaction under `AI_QUEUE_LOCK`**, the same lock the claim uses. The account lease is written with the claim's upsert semantics (`ON CONFLICT (account_lock_key) DO UPDATE`), never a plain `INSERT`, so a stale expired `ai_account_leases` row cannot raise a unique-key error. If either is held the request returns `409 AI_BUSY` and sends nothing. The lease is released, and the heartbeats stopped, in a `finally` on every outcome. The final status update (`SUCCEEDED`, `FAILED`) is conditional on the row still being `RUNNING` with the route's `lease_token`, and for `SUCCEEDED` it runs **in the same transaction as the insert of the proposal-hash rows** (below): if recovery already ended the row `INTERRUPTED` (or it was cancelled), the conditional update changes nothing, the transaction inserts no proposal rows and the route returns a failure instead of overwriting the other status.
     - **Budget and usage (G3):** there is **no manual daily budget**. `manual_reserved` counts pending queued reservations and a manual cap applies only to `QUEUED` rows (`AI_LIMITS.manualQueued`); the only daily cap is for `AUTOMATIC` runs, which document runs never are. The run sets `reserved_day` to the UTC control day, **leaves `manual_reserved` unchanged** (no increment, so no phantom reservation), and records usage in `llm_usage` like a queued run. The only limits that apply are the account and workspace concurrency rules above. This change defines no new daily cap.
     - **Timeout and abort:** it uses `AI_LIMITS.timeoutMs` and aborts the provider call when the client disconnects, marking the run `FAILED` and releasing the lease.
   - **What is persisted (G5):** `ai_runs.snapshot` stays an **immutable, insert-time record** (trigger `ai_runs_immutable_input`, migration 0010, refuses any update of `snapshot`, `snapshot_hash`, `input_versions`, `reserved_day` or identity columns, and this change does not loosen it): it holds only `payloadSha256`, the base revision id and the cited fact ids. Proposal hashes exist only after the provider returns, so they live in a new **hash-only table `ai_document_reword_proposals`** created by the migration of task 1.2, with `workspace_id`, `run_id`, `sentence_id`, `proposal_sha256` (SHA-256 of the canonical JSON of `{text, sourceFactIds}`: the proposed text **and** its citations), a composite foreign key `(workspace_id, run_id)` to `ai_runs(workspace_id, id)` **`ON DELETE CASCADE`** and a unique key `(workspace_id, run_id, sentence_id)`. Its rows are inserted in the same transaction as the conditional `SUCCEEDED` write. The table is added to `DELETION_ORDER` **before `ai_runs`**, to the JSON export, and to backup and restore; clearing or expiring run history (`apps/api/src/ai/history.ts`, which deletes terminal runs with no artifact after the retention period or on a manual clear) cascades its rows. No sentence text, fact text or proposal text is stored. A declined, refused or failed request writes no proposal hashes. **Only `CANDIDATE_CLAIM` sentences are sent for rewording**: `OFFER_REFERENCE` and `BOILERPLATE` sentences are never reworded (they have no citation and would fail the citation rule), so a proposal for one is rejected.
   - **No revision before acceptance:** nothing is added to the draft by the run. A new revision is created only when the person accepts, via an accept request carrying the run id, the base revision id and the proposed sentences with their `sourceFactIds`. The server (1) loads the run record and requires that it belongs to the workspace and targets the base revision; (2) reads the stored hashes from `ai_document_reword_proposals` for that run (if the run or its proposal rows no longer exist because history was cleared or expired, or the run did not end `SUCCEEDED`, it returns the named `409 AI_PROPOSAL_EXPIRED`, never a 500), hashes `{text, sourceFactIds}` of each submitted sentence and requires it to equal the stored `proposal_sha256` for that sentence id, otherwise `422 PROPOSAL_MISMATCH` and nothing is created (altered text, altered or added citations, unrecorded or extra sentences are all refused); (3) re-runs the citation and no-new-fact checks; (4) in one transaction, **locks the logical document row `FOR UPDATE`**, requires the base revision to be still the newest, and inserts one revision rendered as in decision 4, with origin `CODEX` for the accepted sentences. **There is no persisted "consumed" flag**: a second accept of the same run fails because the base revision is no longer the newest and, under a race, because the unique `(workspace_id, document_id, revision)` key rejects the second insert. A proposal the person edits before accepting goes through the ordinary edit route and is stored as `USER_EDITED`. Discarding writes nothing.
   - Requests whose origin is `AUTOMATIC` (scheduled, background, automation policy) are refused with `403 CONSENT_REQUIRES_PERSON` and write no run.
   - `USER_UNSUPPORTED` sentences are not sent. Workspace deletion removes the proposal-hash rows (before `ai_runs`), the run record, the one-off consent rows and `llm_usage` with the other AI rows; no document text exists in assistant records to clean up. While a synchronous run is in flight it holds the request gate, so a workspace deletion request returns `503 DELETION_BUSY` after the existing 30 s wait (a run lasts at most `AI_LIMITS.timeoutMs` plus the grace period); this is safe and is documented rather than aborted.
13. **Language is a column with a check.** One `language` per logical document (`es`/`en`); the builder uses fixed phrase tables per language, and approval validates that generated phrases match. Facts' own text is the person's and is not translated.
14. **Follow-up draft is its own table and phase.** Plain text on the application, fixed templates, copy only. Timing: it may start once the base migration (task 1.2) and the backup work (1.4) are merged to `main`; it needs only 1.2, 1.4 and their dependencies (1.4 depends on the staleness rules 2.3), not the remaining document phases, ships as its own pull request, and is last by default. Its migration is created only then, with the next free number. It is removed by workspace deletion like the other new data.
15. **Concurrency and orphan files.** Approval and accept each run in one transaction that locks the logical `application_documents` row `FOR UPDATE` before checking that the target revision is the newest and before the approval write or the revision insert, so "newest" and the write are atomic. Files are rendered before the revision row is inserted; when the insert loses a race (unique or lock conflict) or fails, the just-rendered text and PDF files are removed, so no unreferenced file remains (workspace deletion would also clear any leftover).
16. **ADR.** Add `docs/decisions/023-application-documents.md` (numbering rechecked on `main`) covering the sentence kinds, approval binding, one-way references, preview-bound approval, request-only selection, the ZIP boundary, workspace-only deletion and the follow-up boundary.

## Risks / Trade-offs

- A second pair of document tables duplicates a little of `document_versions`; accepted to avoid altering a hot table and to keep references one-way. Existing attached resumes are not unified with the new ones, which is stated as a limit.
- "No new fact" checking is heuristic; mitigated by rejecting on any new number, date, proper noun or known skill not in the cited facts, and by mandatory human approval.
- Rendering a PDF and text on every saved revision costs CPU and storage (two small files per revision, all kept because revisions are immutable); documents are small, so accepted. Approval only reads and hashes the stored files. The JSON export includes PDF bytes only for approved and newest-pending revisions (decision 11), so revision history does not grow the artifact total.
- Individual-application deletion is absent from the product; until a later change adds that route (with its own deletion design), users remove documents only by deleting the workspace. Stated as a limit.
- ZIP dependency adds supply-chain surface; prefer a tiny store-only writer with tests.
- Local text fidelity: plain text drops layout; stated as a limit.

## Migration / Rollout

Apply after #129 merges, one task per pull request branching from `main`. No version bump or changelog edit in contributor PRs.

- **Serialization:** task 1.2 (base migration) merges first. Tasks that need the schema (1.3 onward) branch from `main` after it. The follow-up migration (8.1) is created only after 1.2 is merged and takes the next free number then; no two open pull requests may add a migration at the same time.
- **Review gates:** each sensitive pull request (1.2, 1.3, 1.4, 3.1, 3.2, 3.3, 3.5, 4.1, 5.1, 8.1) gets an `opus-reviewer` pass on its diff, with findings fixed or recorded, **before it is merged**, not after.
- **Restore ordering:** the restore task (1.4) depends on the staleness rules (2.3) because restore must recompute `factsHash` and `offerHash` so that documents read as `NEEDS_REVIEW` (computed on read, nothing written by restore) when a cited fact or snapshot did not restore.
- Rollback: the migration is additive and the tables are unreferenced by older code, so unused tables are harmless; before a release, revert the pull request.
- **Test wiring and Chromium:** route tests (3.1, 3.2, 3.4, 3.5, 4.1, 5.1, and the deletion, export and backup tests) inject a fake renderer that returns fixed bytes, so they need no Chromium. Only `application-documents-pdf.test.ts` (3.3) and the approval byte-identity test (3.2) use the real renderer. The `test:application-documents` CI step runs after the Chromium and `poppler-utils` install steps, and `scripts/test/ci-wiring.test.mjs` asserts that order.
- **Test environment gates:** database-backed tests (including `ai-application-documents.test.ts`, which runs in `test:ai` where `platform-build` has no database) reuse the database variable that the neighbouring tests in that script use and skip explicitly without it; the real-Chromium tests (3.2 byte identity, 3.3) are gated by an explicit variable, `CAREER_V090_PDF_TEST` (as used by `ci.yml`), so a local run without Chromium skips them visibly rather than failing or passing silently.
- **Test wiring:** every test file named in the tasks must be reached by a script that CI runs (see the tasks' test-wiring note); the follow-up tests are named `application-documents-follow-up*.test.ts` so the same glob catches them.
